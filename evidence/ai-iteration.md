# След ключевой итерации с ИИ: запись на прогулку

## Исходная задача

Этап 3 плана: дать пользователю возможность выбрать свободный слот, ввести непустое синтетическое ФИО и подтвердить запись. Сервер должен отклонить повторную запись в занятый слот и сохранить первоначальную запись. Формулировка приведена по требованиям `spec.md` и этапу 3 в [PLAN.md](../PLAN.md), а не как дословная цитата запроса.

## Ключевое решение

Сервер выполняет одно условное атомарное обновление SQLite: записывает ФИО и время только для строки выбранного слота, где `booked_by IS NULL`. Если обновлённой строки нет, слот уже занят и сервер возвращает HTTP `409`. Так проверка доступности и запись не разделены на отдельные операции, а повторный запрос не затирает исходное ФИО.

## Изменённые файлы

- `server.js` — проверка входных данных, атомарное обновление свободного слота, ответы HTTP `201` и `409`.
- `public/index.html` — форма записи и элементы управления слотами.
- `public/app.js` — отправка формы, отображение успешного результата и сообщения об отказе.

Файлы перечислены по текущей реализации. История Git содержит один общий коммит реализации MVP, поэтому отдельный коммит только для этапа 3 отсутствует.

## Проверка

В журнале этапа 3 в `PLAN.md` записаны результаты проверки на изолированной временной копии:

1. Первая запись синтетического ФИО вернула HTTP `201`; крайние пробелы в имени были удалены.
2. Повторная запись того же слота вернула HTTP `409`.
3. Последующий `GET /api/today` подтвердил, что в SQLite сохранилось первоначальное ФИО.
4. Пользователь проверил повторную попытку через две вкладки и подтвердил, что появилось сообщение об отказе.

## Что проверил и принял пользователь

По журналу проекта пользователь проверил повторную попытку через две вкладки и подтвердил появление отказа. В последующей итоговой проверке пользователь также подтвердил, что сообщение об отказе отображается. Это фиксирует подтверждённое поведение интерфейса; HTTP-коды и сохранение исходной записи проверялись отдельно на временной копии сервера.
